# BlogServer 网页回报与 IP 封禁设计

日期为 2026-11-21。本文定义目标行为，首版源码已按观察模式接入。配置样例位于 `Server/config/traffic-guard.json`，运行时读取资源目录的 `config/traffic-guard.json`。发布时需要随新版模板和独立回报 JS 一起安装该配置。端到端负载性能预算仍待实测。

## 1. 目标与决策

同一来源 IP 在 **10 分钟滚动窗口**内，累计有 **30 次网页访问在各自的 30 秒宽限期内未回报**，封禁 **1 小时**。首页、文章、归档、分类、相册共用这一门槛，跨页请求累计。封禁在博客 HTTP 层生效，返回 `429` 和剩余等待秒数。搜索爬虫、禁用 JS 的读者和共享出口的访客都可能满足该条件。

这项规则解决反复获取 HTML 的流量问题。文章阅读数另有一个产品决策：维持“请求即计数”，还是改为“收到页面回报才计数”。首发沿用现有口径；观察期结束后可独立切换。回报只能证明客户端完成了协议，能模拟回报的程序仍可取得确认。

## 2. 后端接入与前端协议

| 环节 | 所属组件 | 约定 |
| --- | --- | --- |
| 请求入口 | FeiLib / HTTP 过滤器 | HTTP/1.1 与 HTTP/2 使用同一套 socket 对端地址语义。先检查生效中的封禁，再对受保护页面预留待回报名额，两步都在控制器和阅读计数之前完成。 |
| 页面渲染 | BlogServer / 页面控制器 | 显式登记页面类别。为成功的公开 HTML 页面生成随机 128 位凭据，在模板上下文提供可选字段 `visitId`。旧模板或未登记页面不发凭据，也不记漏报。 |
| 响应交付 | BlogServer / 响应完成回调 | 在实际响应准备发送时激活凭据并起算宽限。渲染失败、重定向、304、HEAD 或发送前已取消均释放预留。异步文章渲染沿用同一完成回调。已交给网络层但用户未收到的页面仍可能成为漏报。 |
| 页面回报 | blogweb / `src/visit-report.ts`（拟新增） | 从 `<meta name="blog-visit" content="…">` 读取凭据。没有该元素便退出。公开模板直接加载轻量入口，独立于评论、统计和 UI 初始化。静态 JS 可缓存，含凭据的 HTML 使用 `Cache-Control: private, no-store`。 |
| 确认 | BlogServer / `POST /_traffic/proof` | 请求体为 32 个小写十六进制字符，类型为 `text/plain`，附带 `X-Blog-Visit: 1`。限制请求体大小，核对 socket 来源、凭据和同源条件。无须设置访客 Cookie。 |

前端每页立即发一次同源 POST，可使用 `fetch` 的 `keepalive`。网络错误或 5xx 最多重试两次，复用原凭据，退避和单次超时合计小于宽限期。首次确认和保留期内同 IP 的成功重试都返回 `204`。错误或未知凭据返回 `403`，超时凭据可统一返回 `403`，错误方法返回 `405`。接口禁止跨站读取和提交，不接受客户端指定文章 ID。脚本下载、页面预加载的静态资源和 GoatCounter 上报均不充当确认。

## 3. 如何计算封禁门槛

每次访问依次经历「预留 → 已签发 → 已确认或漏报 → 回收」。规则按 **(规则 ID，来源 IP)** 聚合。时间比较采用单调时钟。对签发时刻为 `t` 的访问，回报到达服务端的判定时刻早于 `t + grace` 才算及时。等于截止时刻即算漏报。服务端在同一分片锁内先处理已到期事件，再处理本次请求或回报，结果不依赖清理线程先后。

**窗口按漏报发生时刻计算。** 取每次访问的 `deadline = t + grace`。对时刻 `now`，累计 `now - window < deadline <= now` 的漏报。第 30 条漏报触发一次封禁，结束时刻为该事件时刻加 3600 秒。重复请求返回剩余时间，不能延长本次封禁。若工作线程延迟唤醒，则按事件时刻依序补算。进入封禁时清掉该规则该 IP 的待判定访问和漏报计数，期满重新累计。已确认凭据保留短期重试记录。

| 例子 | 结果 |
| --- | --- |
| 一 IP 同时访问 35 页，6 页按时回报 | 29 次漏报，继续放行。 |
| 一 IP 同时访问 35 页，5 页按时回报 | 第 30 次漏报到期时开始封禁。 |
| 已有 29 次漏报，最早的一次恰好移出窗口，又出现 1 次 | 窗口内仍为 29 次。 |
| 一 IP 有 64 个仍处于宽限期的页面，再打开一页 | 暂拒新页面，用 `429` 提示短暂等待；现有凭据仍可回报。该拒绝本身不计漏报。 |
| 请求相册图片、RSS 或 API | 不发凭据。生效中的封禁仅影响配置指定的范围。 |

访问者的 IP 在加载页面后发生改变时，来自新地址的回报无法确认旧访问；单次失配不会直接触发封禁。公网直连使用 socket 对端 IP。若启用反向代理，只有直接对端属于已配置可信 CIDR 时才解析转发地址链，从右向左跳过可信代理。配置缺失或地址格式无效时回退到对端地址并记录异常。现有地址结构使用 IPv4，IPv6 规则需待网络层支持后开放。

## 4. 配置文件

建议在服务资源目录增加 `config/traffic-guard.json`。以下是完整的首版建议值。用户选定了窗口、漏报门槛和封禁时长，其余数值作为上线前校准的初始值。

```json
{
  "version": 1,
  "mode": "observe",
  "rules": [
    {
      "id": "public-pages-without-report",
      "enabled": true,
      "pages": ["home", "article", "archive", "category", "photos"],
      "groupBy": "clientIp",
      "windowSeconds": 600,
      "reportGraceSeconds": 30,
      "maxUnreported": 30,
      "maxPendingPerIp": 64,
      "banSeconds": 3600,
      "blockScopes": ["publicPages", "publicApi"]
    }
  ],
  "clientIp": {
    "source": "socket",
    "forwardedHeader": "X-Forwarded-For",
    "trustedProxyCidrs": [],
    "allowCidrs": ["127.0.0.0/8"]
  },
  "limits": {
    "maxTrackedIps": 4096,
    "maxOutstandingVisits": 16384,
    "maxRecentConfirmations": 16384,
    "confirmationRetentionSeconds": 60
  },
  "persistence": {
    "banFile": "cache/traffic-guard-bans.json",
    "flushIntervalSeconds": 5
  },
  "observability": {
    "requestSampleRate": 0.01,
    "logBanEvents": true
  },
  "articleViews": { "countOn": "pageRequest" }
}
```

- **运行模式。** `off` 停止签发和执行规则。`observe` 签发并记录本应拒绝的事件，但继续服务，包括触及突发上限时的请求；无法分配凭据的访问不计漏报。`enforce` 执行两类 429。从观察切到执行时开启新的计数周期，观察阶段的模拟封禁不会转入生产。
- **规则匹配。** 类别映射到已注册的 GET 页面路由，分类详情也属于 `category`。静态文件、证书验证、RSS、后台及错误页面不签发凭据。多个规则可保护不同类别。首版拒绝有重叠页面的启用规则，避免一页被重复计数。多个仍有效的封禁覆盖同一请求时，返回其中最长的剩余时间。白名单优先。
- **加载校验。** 启动和热加载共用解析器，检查类型、枚举、唯一 ID、路由类别、CIDR 及数值范围。要求 `0 < grace < window`、`maxPendingPerIp >= maxUnreported`、单规则限制不超过全局容量。拒绝缺少可信代理列表的转发模式。相对文件路径以服务资源目录为基准。
- **生效边界。** 后台完整验证后原子替换只读配置。无效热加载保留有效版本。首启配置缺失或无效时保持网站可用，关闭规则并输出明确诊断。新凭据采用新配置；规则时间参数变化时，以配置代际隔离在途计数并按原参数排空。既有真实封禁保留原到期时刻。`off` 立即停止拦截。重新启用的历史封禁语义须可预测，建议只恢复仍有效的真实封禁；紧急白名单即时覆盖拦截。

## 5. 性能、容量和故障处理

使用按来源 IP 哈希的分片表。每个分片拥有 IP 状态、凭据索引和按到期时刻排列的事件；签发、确认和封禁转换在同一分片内完成。已有封禁查找和凭据匹配期望为 O(1)。用时间桶调度到期事件，每次仅处理到期的记录。单 IP 漏报历史在触发阈值后即清理，待回报数有单独上限。普通请求无需扫描所有 IP，资源响应也无需查找 HTML 标签。

请求入口先按路由范围走快速路径。凭据仅为受保护页面生成。只把不可变的封禁事件或待刷盘标记交给后台，网络线程不做文件 I/O。后台合并刷新，用临时文件加原子替换保存有效封禁和墙钟到期值。重启时转换为单调时钟剩余时长并丢弃过期项。崩溃可能损失一个刷盘周期内的新封禁，正常退出应等待最后一次刷新。待回报状态保存在内存，重启前发出的凭据作废，不追记漏报。

全局容量耗尽时，继续执行已有封禁，允许未能跟踪的新访问通过，计入容量告警。绝不能把未发凭据的页面记入漏报。限制近期确认表、日志队列和定时事件的大小，消费或取消凭据时同步回收定时节点，避免高频成功回报留下大量空事件。观察模式也遵守相同容量上限。

保留签发、确认、漏报、超时回报、短期限流、实际封禁、模拟封禁、容量跳过、刷盘失败等计数。日志可以记录规则 ID、时间、来源 IP 和触发数量，不写凭据或回报请求体。规则集中触发时可根据日志执行定向解封或加白；使用内存内解封操作并同步更新持久化，避免旧文件在重启时恢复已解除的封禁。

## 6. 阅读数兼容性

`pageRequest` 模式沿用文章详情控制器现有计数，入口拦截必须早于该控制器。`confirmedReport` 模式从签发记录读取文章 ID，在首次及时确认时计数。其他页面及重试不会增加文章阅读数。为避免确认时数据库写入失败却永久丢掉计数，可在同一事务用唯一访问 ID 去重并递增阅读数，提交后标为确认、返回成功。重试和并发确认必须走同一去重机制。仅对开启此口径的文章访问引入这项写入，定期回收超过重试期限的去重记录。

确认口径会排除禁用 JavaScript 的读者。配置应拒绝在 `off` 或文章未接入回报时单独开启它。上线初期可并行观察“文章请求数／成功回报数”，再决定是否切换展示口径。历史阅读数不在规则迁移范围内。

## 7. 发布与验收

1. 先发布前端入口、模板和后端协议兼容能力。只有已确认含回报入口的模板才标为可跟踪。旧后端或无凭据页面可以正常浏览。检查不同访客的动态 HTML 没有复用同一凭据。
2. 用观察模式验证首页、文章、归档、分类、相册的回报率。覆盖 HTTP/1.1、HTTP/2、弱网重试、多个标签页、同 IP 多访客和前端资源加载失败。验证 RSS、静态资源、404 和管理路由均不产生漏报。观察阶段如果全站回报骤降，先定位前端资源或回报接口故障。
3. 在隔离环境用可控时钟覆盖第 29／30 次、截止时刻两侧、窗口恰好移出、突发限流、封禁到期、重复凭据、跨 IP、热加载及重启。再通过真实浏览器确认执行脚本确实收到 204，通过不执行脚本的客户端确认受保护请求返回 429、携带合理的 `Retry-After`，且被拒文章不加阅读数。
4. 以相同数据、并发和请求组成对比 `off / observe / enforce`。记录吞吐量、P95/P99 延迟、CPU、峰值内存、锁等待和刷盘队列。分别测正常读者、单 IP 突发、多 IP 达容量及重静态资源流量，同时核对内存上限和容量释放。尚无该设计的实测性能数据。
5. 确认前端回报覆盖、误封情况和性能结果后切至 `enforce`。遇到集中误封可热切 `observe` 立即停止拒绝，保留诊断数据。验证配置回退以及白名单、解封和自动到期均真实生效。

## 9. 首版实现与运维

首版使用 16 个 IP 分片，各分片的凭据采用哈希查找，单 IP 到期事件采用可删除的有序表。确认会立即删除对应到期节点，避免成功访问留下空事件。后台每秒按分片清理，工作量受全局 IP 和记录数量限制；该版本的清理会遍历受限的 IP 表，尚未采用跨 IP 时间轮。

请求上下文在控制器之前保存预留凭据，复制异步请求时共享同一上下文。上下文释放时撤销未激活名额，成功页面在准备发送时起算宽限。模板通过显式参数输出 meta。发送前仅对受跟踪页面检查凭据是否确实存在，兼容尚未更新的模板。前端构建产出独立的 `assets/visit-report.js`，避免回报入口被合并进 UI 依赖。

配置每秒检查修改时间。首版最多保留 8 个在途配置代际，跨代际共享总容量。连续高频修改超过此上限会保留有效配置并记录诊断，`off` 始终可切换。旧代际按最大封禁与窗口期限退出；真实封禁保持原到期，观察模式的模拟封禁不会参与执行拦截。配置不存在或首启无效时以关闭状态提供网站服务。

本机维护接口使用真实 socket 来源限制到 `127.0.0.0/8`，适合当前直连部署通过 SSH 在服务器本机调用。转发模式下，属于可信代理的连接对端也会被拒绝，避免本机反向代理转发的公网请求取得维护权限；该模式需要另行安排独立维护入口。

- `GET /_traffic/status` 返回当前模式、IP/待回报/近期确认容量、成功确认请求数、拒绝请求数和容量跳过次数。
- `POST /_traffic/unban` 使用 `X-Blog-Visit: 1`，请求体为待解封 IPv4 文本，清除所有在途代际中该地址的封禁及漏报状态。后台下一次刷盘保存结果，异常掉电可能损失该周期内的解封或新封禁。
- 首版代理模式仅支持 IPv4 的 `X-Forwarded-For` 链。公开 API 的封禁范围使用已知公开 GET 路由，管理 API 继续走现有鉴权。

可选 `confirmedReport` 会按需创建 `ConfirmedArticleVisits` 表，保存服务端签发凭据与文章 ID 的关联。首次确认在 SQLite 事务中递增阅读数并标记凭据，事务失败可以重试。该模式为数据库写入增加负担，默认 `pageRequest` 沿用现行口径。

## 11. 请求头阶段快速拦截

FeiLib 新增 `FHttpServer::setHeadersFilterCB`。HTTP/1 在请求头完成、Content-Length 对应内存预留和请求体解析之前调用。命中后返回 429 并关闭该连接，避免未读取的请求体污染 keep-alive 中的下一条请求。HTTP/2 在 HEADERS 解码完成后调用，对被拒的 stream 返回 429，丢弃该 stream 后续 DATA 的应用层内容，同时继续处理同连接的其他 stream。HPACK、帧解析及连接级流控仍由 nghttp2 维护。

TrafficGuard 将执行模式的有效封禁汇总为独立的 IPv4 数值键哈希表。表项区分公开页面与公开 API 的到期时间，后台原子发布只读快照。请求头 Hook 做路径分类、来源/白名单校验和一次哈希查询，不遍历规则或更新漏报状态。直连模式直接使用 socket 地址的数值键。快照周期约一秒，实际受调度和后台任务耗时影响，原有控制器前过滤器在刷新前仍执行完整判定。解封同步清除快速表，后台重建；观察和关闭模式均不执行快速拒绝。

保留现有的静态资源、RSS、回报和维护接口排除范围。由于判定依赖路径和代理头，TCP、TLS 与请求头解析仍需执行。该实现使用原子 shared_ptr 发布快照，不承诺底层操作完全无锁。

隔离内存探针在本地 WSL/Linux 中装入 4096 个 IP、16384 条待回报记录，RSS 从约 3.7 MiB 增至 14.3 MiB，增量约 10.6 MiB。到期后逻辑条目为零，RSS 仍约 14.4 MiB，与分配器保留高水位内存的表现相符。此数据仅覆盖规则状态，不含整个 HTTP 服务或可选 SQLite 计数开销。默认容量受限，但实际 RSS 仍应通过持续负载监测确认。

随后连续五轮填满并清理同样规模的状态，RSS 为 14688、14688、14688、14688、14692 KiB，各轮 IP 和待回报条目均回到零。该有限轮次探针没有出现持续按轮增长，不能替代长期服务器负载测试。

仍需关注可选 `confirmedReport` 模式的确认事务。当前事务回调位于对应 IP 分片锁内，数据库锁等待会延长该分片的持锁时间。默认 `pageRequest` 不执行该事务。正常放行流量仍需要规则计算和到期处理；快速表主要缩短已经封禁的请求路径。
